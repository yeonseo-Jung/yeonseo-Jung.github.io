비즈니스 문제 — 복잡한 운용 전략을 매출 가능한 상품으로 전환

B2C 핀테크 플랫폼의 핵심 병목은 전략의 부재가 아니라 사용자가 전략을 이해하고 설정하기까지의 학습 비용이었습니다. 라이트 유저는 자산군 선택, 리밸런싱, 리스크 조절, 시장 국면 해석을 직접 수행하기 어렵고, 그 결과 서비스 탐색 후 실제 운용 전환까지 이어지는 비율이 낮아집니다. 이 문제를 해결하기 위해 기관형 자산배분 프레임워크를 3-클릭 구독형 운용 상품으로 재구성했습니다.

이 프로젝트의 핵심은 단순히 백테스트 수익률을 높이는 것이 아니라, 도메인 가설 → 데이터 검증 → 포트폴리오 산출 → 리스크 오버레이 → 주문 위임 → 라이브 모니터링까지 이어지는 제품형 운용 엔진을 만드는 것이었습니다. 결과적으로 1,600+ 계좌 운용 인프라 내에서 라이브 적용되었고, 구독형 운용 상품의 AUM 500억+ 달성에 기여했습니다.

1,600+ 계좌 운용 인프라 내 라이브 적용 AUM 500억+ 3-클릭 구독형 운용 UX 시뮬레이션 4.15y · 라이브 1.36y 정합 검증
문제 해결 과정 — 문제 정의에서 회고까지
문제 정의 신규·라이트 유저는 전략을 직접 설계하고 운용 규칙을 이해하는 데 높은 학습 비용을 겪었고, 이는 서비스 탐색 후 실제 운용 전환을 막는 병목이었습니다.
가설 수립 기관형 자산배분 프레임워크를 사용자가 이해 가능한 구독형 상품 구조로 추상화하면, 전략 설계 부담을 낮추고 실제 운용 전환과 유지율을 높일 수 있다고 판단했습니다.
실험 설계 거시 레짐, 공분산 전처리, 리스크 예산, 꼬리 위험 오버레이를 결합한 운용 엔진을 만들고, 백테스트와 라이브 운용 흐름을 동일한 데이터 기준으로 검증했습니다. 전략 산출물은 주문 실행 인프라로 위임해 실제 계좌 운용까지 연결했습니다.
성과 측정 1,600+ 계좌 라이브 운용 환경에서 적용되었고, 구독형 운용 상품 AUM 500억+ 및 서비스 매출 40% 기여로 이어졌습니다.
회고 및 개선 단기 수익률이 높은 전략보다 사용자가 이해하고 지속 운용할 수 있는 설명 가능성, 리스크 안정성, 라이브 재현성이 더 중요하다고 판단했습니다. 이후 운용 데이터 기반으로 자산군 상관구조, 성과 기여도, 리스크 기여도를 분석하며 자산 구성과 상품 구조를 점진 개선했습니다.
문제 해결 방법론 — 금융 가설을 시스템 모듈로 변환
  • →H1. 시장 상태 조건부 성과 — 자산의 기대수익은 무조건부 평균이 아니라 성장·인플레 국면에 따라 다른 조건부 분포로 나타난다고 가정했습니다. 이를 Regime Detector 모듈로 분리해 포트폴리오 가중치의 입력으로 사용했습니다.
  • →H2. 자본 비중 균등 ≠ 리스크 균등 — 동일 자본 비중이라도 변동성과 상관구조에 따라 자산별 리스크 기여도가 크게 달라집니다. 따라서 자산군 간 리스크 예산을 먼저 맞추고, 자산군 내부에서는 효율성 신호로 tilt하는 2단계 배분 구조를 채택했습니다.
  • →H3. 최적화 품질은 입력 행렬 품질에 종속 — 자산 수 대비 관측 기간이 제한된 환경에서는 공분산 행렬이 노이즈에 민감합니다. EWM·Shrinkage·RMT·PD 보정을 거치는 입력 전처리 파이프라인을 별도 모듈로 두었습니다.
  • →H4. 상시 헤지보다 조건부 노출 축소 — 전 기간 헤지는 비용 누적 문제가 있어, 꼬리 위험 임계 초과 시에만 노출을 낮추는 risk overlay를 적용했습니다.
  • →H5. 데이터 최적해와 전략적 prior 결합 — 단일 표본의 극단 비중을 완화하기 위해 데이터 기반 산출값과 전략적 사전을 볼록결합해 실서비스에서 설명 가능한 비중 변화를 유도했습니다.

해석 가능한 레짐 감지 — 서비스 신뢰성 우선
HMM·GMM 같은 비지도 방식은 연구 단계에서 유용하지만, 출력 클러스터에 경제적 의미를 사후 부여해야 합니다. 사용자가 이해할 수 있는 운용 상품에서는 설명 가능성이 중요하므로, 성장·인플레 축을 설계 단계에서 직접 반영한 규칙 기반 레짐 감지를 우선 적용했습니다. 이는 투자 설명, 운영 모니터링, 파라미터 변경 승인 과정에서 모두 재사용 가능한 의사결정 언어를 제공합니다.
공분산 입력 품질 — 4단계 전처리
최적화 알고리즘 자체보다 입력 행렬의 품질이 최종 비중 안정성에 더 큰 영향을 준다고 판단했습니다. 최근성 반영을 위한 EWM, 표본 불안정성 완화를 위한 Ledoit-Wolf shrinkage, 무작위 행렬 이론 기반 노이즈 제거, 솔버 조건을 만족시키는 positive definite 보정을 순차 적용했습니다. 각 단계는 서로 다른 문제를 해결하도록 분리되어, 입력 추정 방식만 교체해도 전체 엔진은 유지됩니다.
리스크 예산 — 자산군 간 균형과 내부 효율성 분리
자산군 간에는 리스크 기여도를 기준으로 균형을 맞추고, 자산군 내부에서는 Sharpe·모멘텀·상관 구조를 반영해 효율성이 높은 자산으로 일부 tilt했습니다. 이 구조는 1/N 자본 배분의 단순함과 평균-분산 최적화의 과민성을 모두 피하면서, 상품 설명 가능성과 실전 운용 안정성을 동시에 확보하기 위한 절충입니다.
백테스트↔라이브 정합성 — 상태 3계층 분리
최신 최적화 산출물, 직전 승인 비중, 실제 포지션 상태를 분리해 저장했습니다. 매일 최적화는 수행하되, 직전 승인 비중 대비 편차가 임계값 이하이면 리밸런싱을 보류하는 deadband를 두어 turnover를 관리했습니다. 외부 지표는 발표일 기준으로 available-at 시점을 맞췄고, 시그널 생성 후 다음 거래일 체결 원칙을 적용해 시뮬레이션과 라이브의 데이터 흐름을 일치시켰습니다.

프로젝트 배경

계좌 수가 수백에서 1,600+ 규모로 커지면서, 시그널 생성과 주문 집행을 같은 실행 흐름에 묶는 구조는 확장성과 운영 통제 측면에서 한계가 명확했습니다. 코인은 24/7 이벤트 매매가 필요하고, 주식은 장 세션과 리밸런싱 주기에 맞춰야 했기 때문에 자산군별 실행 특성을 하나의 엔진으로 처리하기 어려웠습니다. 이를 해결하기 위해 시그널 생성부와 주문 집행부를 물리적으로 분리하고, RabbitMQ 기반 pub/sub 1:N 구조로 시그널 1개를 다수 계좌에 안정적으로 배포하는 실행 계층을 설계했습니다.

현재 구조는 1,600+ 계좌와 6개 외부 거래 채널을 기준으로 운용되며, 주문 집행 영역에서 운영 로그 기준 관측된 메시지 유실 0건을 유지했습니다. 월평균 거래대금은 약 5천억 규모로, 단일 계좌·단일 거래소 중심의 스크립트를 계좌 단위·거래소 단위로 수평 확장 가능한 운영 시스템으로 전환한 프로젝트입니다.

1,600+ 계좌 월평균 거래대금 약 5천억 6개 거래소/증권사 연동 관측 메시지 유실 0건
문제 해결 관점 — 실행 신뢰성과 확장성 확보
문제 계좌 수가 증가하면서 시그널 생성, 계좌별 주문 판단, 외부 거래 채널 연동, 주문·체결 상태 기록이 같은 실행 흐름에 묶여 확장성과 장애 격리성이 약해졌습니다.
설계 판단 시그널 생성은 stateless하게 유지하고, 주문 side effect와 계좌 상태는 execution layer에서만 관리하도록 경계를 분리했습니다. 이를 통해 전략 추가, 계좌 확장, 거래소 연동을 실행 계층의 재설계 없이 처리할 수 있다고 판단했습니다.
구현 RabbitMQ 기반 pub/sub 1:N 구조로 시그널을 fanout하고, manual ACK, DLQ, 시간 슬롯 멱등성, 계좌 단위 Bulkhead를 적용했습니다. 자산군별 실행 특성은 별도 정책으로 분리했습니다.
운영 성과 1,600+ 계좌, 6개 외부 거래 채널 기준으로 운용되었고, 주문 집행 영역에서 운영 로그 기준 관측 메시지 유실 0건, 월평균 거래대금 약 5천억 규모를 처리했습니다.
개선 초기 Python 실행 계층은 빠른 제품화에는 유리했지만, 고빈도 코인 주문 영역에서는 런타임 일관성, 메모리, 배포 이미지 크기 문제가 커졌습니다. 이후 Rust 기반 실행 계층을 Strangler Fig 방식으로 점진 전환해 운영 비용과 타입 안정성을 개선했습니다.
아키텍처 — Signal Layer와 Execution Layer 분리
시그널 생성과 주문 실행을 경계로 분리해, 전략 추가·거래소 추가·계좌 확장을 실행 계층의 재설계 없이 처리하도록 구성했습니다.
실행 계층 보완 — 자산군별 실행 특성과 운영 보조 계층
위 구조도는 대표 흐름을 단순화해 Signal Layer와 Execution Layer의 경계를 먼저 보여주기 위한 것입니다. 실제 구현에서는 자산군별 실행 특성과 운영 보조 계층을 분리해, 주문 실행 경로와 관측·저장 경로가 서로의 책임을 침범하지 않도록 설계했습니다.
  • →주식 실행 경로 — 장 세션, 휴장일, 리밸런싱 주기, 분할 주문을 고려해 장중 실행 가능 시간과 TWAP 성격의 주문 분산을 별도 정책으로 관리했습니다.
  • →코인 실행 경로 — 24/7 이벤트 기반 시장을 전제로 포지션 델타, 레버리지, 거래소별 주문 규격, 실시간 잔고 동기화를 execution worker 내부에서 처리했습니다.
  • →저장 계층 — MySQL은 주문·체결·계좌 상태의 기준 기록으로 사용하고, Redis는 실시간 가격 캐시와 단기 상태 조회 용도로 제한해 RabbitMQ의 메시지 전달 책임과 혼동되지 않도록 분리했습니다.
  • →관측성 계층 — Prometheus·Grafana·Slack Alert는 핵심 주문 경로와 분리된 운영 보조 계층으로 두어, 처리량·지연·DLQ·계좌별 실패율을 모니터링하고 이상 징후를 빠르게 확인할 수 있게 했습니다.
따라서 대표 구조도는 확장 가능한 실행 경계를 보여주고, 이 보완 설명은 기존 구현의 세부 요소인 주식/코인 실행 차이, 저장소, 캐시, 관측성의 책임 경계를 함께 명시하기 위한 장치입니다.
핵심 설계 판단
메시징 신뢰성 — at-least-once + 멱등성
금융 주문 도메인은 메시지 한 건이 실제 자산 상태를 바꾸므로, 브로커 ACK만으로는 충분하지 않았습니다. Publisher confirm으로 송신 확인을 받고, consumer는 manual ACK로 처리 완료 시점을 명시했습니다. 중복 전달 가능성은 시간 슬롯·계좌·전략·시그널 ID를 결합한 멱등성 키로 흡수해 at-least-once 전달과 중복 주문 억제를 동시에 만족하도록 설계했습니다.
계좌 단위 Bulkhead — 영향 범위 제한
계좌 상태, 주문 가능 수량, 포지션 동기화, 쿨다운을 계좌별로 분리했습니다. 특정 계좌의 상태 변화가 전체 루프의 처리량이나 다른 계좌 주문 판단에 영향을 주지 않도록 설계했으며, 수평 확장 단위도 계좌·거래소 기준으로 나눴습니다.
ML Serving 통합 — 전략 신호의 제품화
XGBoost·LightGBM 앙상블 모델을 단순 연구 코드가 아니라 프로덕션 시그널 파이프라인의 일부로 통합했습니다. 모델 파일, 피처 버전, 임계값, 롤백 포인터를 함께 저장해 동일 모델을 재현할 수 있게 했고, 신호 생성 이후에는 확률 보정과 상태 전이 필터를 적용해 반복 진입과 과대 노출을 억제했습니다.
Python → Rust 점진 전환

Phase 1의 Python 기반 실행 계층은 빠른 제품화와 거래소 SDK 연동에는 유리했지만, 고빈도 코인 주문 실행 영역에서는 비동기 런타임 일관성, 타입 계약, 메모리 사용량, 배포 이미지 크기 측면에서 개선 여지가 컸습니다. 전체 시스템을 한 번에 바꾸지 않고, 코인 거래 실행 계층을 우선 전환 대상으로 제한했습니다.

Rust 전환은 Strangler Fig 방식으로 진행했습니다. Python 서비스와 Rust 서비스가 RabbitMQ 경계를 기준으로 공존하게 두고, 환경 변수와 라우팅 정책으로 소비 주체를 전환할 수 있게 했습니다. 거래소 어댑터는 trait으로 계약을 고정하고, DB는 sqlx 기반 정적 쿼리 검증을 사용해 런타임 의존성을 줄였습니다.

프로젝트 배경

기존 데이터 수집·가공 로직은 두 개의 레거시 코드베이스에 분산되어 있었고, 스케줄링·DB 접근·파일 저장·외부 API 호출·데이터 검증이 서로 강하게 결합되어 있었습니다. 기능은 동작했지만, 신규 데이터 소스 추가나 백필, 재현 가능한 실행 이력 확보, 스토리지 전환 같은 운영 요구가 커질수록 구조적 비용이 증가했습니다.

이를 Airflow 기반 데이터 플랫폼으로 통합하면서, 단순 배치 스크립트를 DAG 기반 오케스트레이션 · 중앙화된 DB 세션 관리 · 스토리지 추상화 · 데이터 품질 게이트로 재구성했습니다. 목표는 특정 배치를 고치는 것이 아니라, 향후 데이터 마켓·피처 스토어로 확장 가능한 표준 실행 계층을 만드는 것이었습니다.

문제 해결 관점 — 데이터 플랫폼 확장 기반 구축
문제 실시간 데이터와 외부 API 기반 정형 데이터 수집·적재 로직이 레거시 코드에 분산되어 있어, 신규 데이터 소스 추가, 백필, 품질 검증, 스토리지 전환이 매번 높은 운영 비용을 만들었습니다.
구조적 판단 수집·검증·저장·메타데이터 추적 책임을 공통 실행 계층으로 분리하면, 데이터 소스가 늘어나도 재현 가능한 방식으로 운영할 수 있고 추후 피처 스토어/데이터 마켓 확장 기반을 만들 수 있다고 판단했습니다.
실행 설계 Airflow DAG, Sensor, TaskGroup, SQLAlchemy 세션 팩토리, Storage Adapter, Data Quality Gate를 도입해 외부 API 수집 → 정제 → 적재 → 검증 → 산출물 추적 흐름을 표준화했습니다.
운영 성과 프로덕션 전환 후 레거시 파이프라인 2종을 폐기했고, 데이터 품질 게이트, 백필 경로, 스토리지 전환 기준을 공통화했습니다.
확장 방향 단순히 Airflow로 이관하는 것보다 데이터 소스·실행 시각·산출물 위치·검증 결과를 메타데이터로 남기는 구조를 우선했습니다. 이를 기반으로 추후 데이터 마켓/피처 스토어로 확장 가능한 실행 표준을 마련했습니다.
Before / After 아키텍처
레거시 배치 코드를 단순 이관한 것이 아니라, 실행·검증·저장·추적 책임을 공통 플랫폼 레이어로 분리했습니다.
핵심 설계 판단
Celery Beat → Apache Airflow
단순 주기 실행은 배치가 늘어날수록 의존성, 실행 순서, 백필, 산출물 추적을 코드 내부 규칙에 의존하게 만듭니다. Airflow를 도입해 DAG 의존성·실행 이력·재시도 정책·백필을 플랫폼 레벨에서 관리하도록 전환했습니다. Managed 서비스 대신 자체 운영을 선택한 이유는 기존 Docker Compose 기반 인프라와 비용 구조, 사내 배치 규모를 고려했을 때 운영 복잡도 대비 통제 가능성이 더 높았기 때문입니다.
DB 연결 중앙화 · 커넥션 풀 표준화
레거시 코드는 배치별로 DB 연결 생성 방식이 달라 커넥션 정책을 일관되게 관리하기 어려웠습니다. 공통 세션 팩토리와 repository 경계를 두어 모든 DAG가 동일한 풀·트랜잭션 정책을 사용하게 했고, 시장 데이터 원문과 메타데이터를 분리해 OLTP 부하와 분석 워크로드가 섞이지 않도록 했습니다.
스토리지 추상화 — S3 / Azure Blob / Local 전환
데이터 산출물이 특정 파일 시스템에 결합되면 클라우드 스토리지 전환과 백필 재현성이 모두 약해집니다. Storage adapter를 두어 저장소 구현을 교체 가능하게 만들고, 산출물 경로·데이터 소스·실행 시각·버전을 메타데이터로 기록했습니다. 이를 통해 동일 DAG가 운영 환경과 재처리 환경에서 같은 계약으로 동작하도록 구성했습니다.
데이터 품질 게이트 — 적재 전 검증
외부 데이터는 API 문서와 실제 응답이 다를 수 있고, 소스별 결측·범위·단위 차이가 존재합니다. 따라서 row count, schema, key coverage, 날짜 coverage, 값 범위 검사를 표준 게이트로 두었습니다. 품질 기준을 통과한 데이터만 downstream 테이블과 파일 산출물로 이동시키고, 기준 미달 데이터는 별도 검토 큐로 분리합니다.
