1. 시험·인증기관 레거시 ERP 운영 데이터 이관 운영 반영

위시켓 AIDP · 2026.06–2026.08 · 냉동공조 분야 시험·인증기관 · 이관 계획·런북·ETL·검증·고객 보고 담당

문제

2013년부터 쌓인 시험 이력이 레거시 SQL Server에 있었고, 신규 ERP(Next.js · Supabase/PostgreSQL)로 옮겨 운영을 전환해야 했습니다. 운영 환경은 하나뿐이어서 이관 실패가 곧 고객 업무 중단이었습니다.

설계 결정

  • 게이트 분리 — Docker MSSQL 2022로 만든 로컬 랩에서 G0–G5 게이트를 모두 통과한 뒤에만 운영 DB(G6–G7)를 건드리도록 순서를 고정했습니다.
  • 사이드맵 — 앱 스키마에 레거시 컬럼을 추가하지 않고 migration_id_map 테이블로 레거시 키 ↔ 신규 키를 추적했습니다. 앱 코드에 이관 흔적이 남지 않고, 행 단위 대조와 재실행이 가능해집니다.
  • 4단계 검증 — 건수 대조 → 금액 합계 → 사이드맵 기준 행 단위 대조 → FK·enum 무결성. 검증기가 실제로 오류를 잡는지 확인하려고 변조 1건을 넣어 실패하는지 보는 역검증을 함께 돌렸습니다.

2. 제조·유통 그룹 ERP 이관·재고 컷오버 운영 반영

위시켓 AIDP · 2026.07–2026.10 · 4개 법인 제조·유통 그룹 · ERP 담당(코드·Odoo 연동 계약·이관·릴리즈), 2026-10-14 인계

문제

법인별로 ECOUNT(SaaS ERP), 자체 WMS(MSSQL), 레거시 PHP ERP에 흩어진 거래·재고를 Odoo 19 기반 신규 ERP로 옮겨야 했습니다. 원장이 서로 다른 시스템 세 개라 "같은 데이터"의 기준부터 맞춰야 했습니다.

ECOUNT → Odoo 거래 이관

  • 운영 반영 순서: 사전 점검(참조 ID 실재 확인) → 스냅샷 백업 → 운영 환경에서 롤백을 먼저 실연 → 거래처 동기화 → 전량 적재 → 다단계 검증 → 라인 단위 대사.
  • 결과: 구매 2,027 + 판매 3,192 = 5,219문서 · 23,130라인, 품목·수량·공급가액 전량 일치(불일치 0, 중복 0).
  • VAT 반올림 차이 151라인은 원인과 영향 범위를 기록하고 수용 판정을 남겼습니다. 차이를 숨기지 않고 분류하는 것을 대사 원칙으로 두었습니다.
  • 생산지시는 DB 직접 입력 대신 UI 경로로 이관했습니다. 생산지시 1건에 Odoo RPC 10개 이상이 엮여 있어, 직접 입력하면 Odoo 내부 상태와 어긋날 위험이 컸습니다.

기초재고 컷오버

  • ECOUNT 209 + WMS 244 + 기적재 3 = 456개 재고 좌표(품목 · 위치 · 로트)를 두 원천에서 합쳐 적재했습니다.
  • 재개 가능한 실행 원장, go/no-go 게이트, 롤백 지점, 산출물 해시를 갖춘 컷오버 스크립트를 작성했습니다.
  • 결과: 기대값 대비 456/456 일치(초과·부족·누락·예상 외 0).

3. ERP 에이전트 쓰기 통제 계층 staging 검증

위시켓 AIDP · 2026.08–2026.10 · 2번과 같은 ERP · 설계·구현 단독

문제

AI 에이전트가 ERP 데이터를 바꾸게 하려면, 모델 출력이 곧바로 DB 쓰기가 되는 구조를 막아야 했습니다. 잘못된 쓰기는 재고·회계에 바로 반영되고, 누가 무엇을 승인했는지가 남아야 합니다.

설계

  • 모든 에이전트 쓰기를 plan → authorization → commit 3단계로 강제했습니다. 에이전트는 변경 계획만 만들고, 사람이 승인한 계획만 서버가 실행합니다.
  • 승인은 Slack 카드로 받고, 카드 응답은 HMAC 서명으로 위변조를 막았습니다. 계획·승인·실행 기록은 원장 테이블에 남깁니다.
  • 원장 스키마 마이그레이션 32개와, 제어면 코드(l2/** 79커밋, API 34커밋)를 단독으로 작성했습니다.
Next.js API RoutesPostgreSQLHMACSlack APIHuman-in-the-loop

4. 소비재 브랜드 AI 데이터 워크스페이스 구축 중

위시켓 AIDP · 2026.08–현재 · 다채널 유통 소비재 브랜드 · 요구사항 인터뷰부터 DB·API·웹·수집기·에이전트·인프라까지 단독

문제

판매·재고·정산 데이터가 ERP, 물류, 판매 채널 포털 등 6곳에 흩어져 있고, 담당자가 엑셀로 손으로 합치고 있었습니다. 목표는 원천을 한곳에 모으고, 현업이 자연어로 질문해도 틀린 숫자를 내놓지 않는 조회 경로를 만드는 것입니다.

설계 결정

  • 모델은 SQL을 실행하지 않음 — LLM은 질문을 조회 계획(데이터셋 · 동작 · 조건)으로만 바꾸고, 서버가 카탈로그 기준으로 계획을 검증한 뒤 실행합니다. 답할 수 없는 질문과 데이터셋을 넘나드는 질문은 모델 판단과 별개로 서버가 차단합니다.
  • 데이터 경계 — 원천 시스템은 읽기 전용으로만 연결하고, 계정·개인정보는 모델 입력에서 뺍니다. 고객 변경 요청의 판정은 규칙 엔진이 하고 LLM은 판정하지 않습니다. 모델 CLI는 도구·MCP·훅을 끈 격리 상태로 호출합니다.
  • 저장소 — 운영 데이터는 PostgreSQL, 분석 질의는 DuckDB로 나누고, 두 엔진의 결과가 같은지 대조하는 테스트를 두었습니다.
  • 모델 경로 교체 — 고객 AWS 계정에서 Bedrock Claude를 쓸 수 없다는 MSP 회신을 받고, 모델 경로를 Bedrock의 GPT 계열과 OpenAI Agents SDK로 바꿨습니다.

평가

자연어 조회 90문항(답 가능 · 모호 · 답 불가 · 교차 질문)으로 백엔드를 비교했습니다.

5. 유지보수 요청 LLM 트리아지 파이프라인 셰도우 운영

위시켓 AIDP · 2026.08–현재 · 2번 고객의 유지보수 티켓 대상 · 설계·구현 단독

문제

고객 유지보수 요청이 들어오면 사람이 매번 요구가 명확한지, 중복인지, 위험한지 판단한 뒤 착수했습니다. 이 판정과 답변 초안을 자동화해 착수 시간을 줄이되, 잘못된 자동 착수는 막아야 했습니다.

설계

  • 30분 주기로 요청을 가져와 모호성 · 중복 · 난이도 · 리스크를 판정하고 답변 초안과 작업 워커 제안을 만듭니다. 판정마다 토큰·비용을 원장(SQLite)에 남기고 예산을 관리합니다.
  • 판정 엔진은 실측 비용으로 골랐습니다(claude -p 호출당 약 $0.19 → 구독 기반 codex exec).
  • 가드레일: dry-run 기본, 정지 마커, 근거 없는 판정 차단(근거 게이트), 발송 채널 허용 목록.

평가와 판단

  • 과거 요청 204건 백테스트: 게이트 통과 4.4%, 사람 판단 대비 과잉 차단 95.1%, 과소 차단 0.
  • 원인 분석: 204건 중 70%가 법인 판별 단계에서 범위 밖으로 빠졌고, 통과율을 바꾸는 축은 리스크 하나뿐이었습니다(단독 제거 시 4.3% → 11.2%). 거절 사례가 11%뿐이라 축별 검정력도 부족했습니다.
  • 판단: 쓰기 모드는 2일 시험 후 멈추고 셰도우 모드로 전환했습니다. 13일 셰도우 대조에서 사람 판단과 방향 일치는 70.3%입니다.
  • 규칙 변경은 같은 티켓을 재판정하는 A/B로 확인했습니다. 53쌍 중 리스크 상향 6건이 규칙 의도와 반대여서 개별 검증 대상으로 남겼습니다.

6. 에이전트용 헤드리스 접근 계층 운영 반영

위시켓 AIDP · 2026.07–2026.11 · 사내 딜리버리 어드민(Next.js · PostgreSQL) · 인증·읽기 평면 담당(부분 기여)

STOA Investment · 2023–2026.06 · 실행 계층 설계·구현·운영 주도

문제

계좌가 수백에서 1,600개 이상으로 늘면서, 시그널 생성 · 계좌별 주문 판단 · 거래소 연동 · 체결 기록이 하나의 실행 흐름에 묶여 있어 확장성과 장애 격리가 약했습니다. 주문 메시지는 한 건이 곧 실제 자산 변경이라, 중복 실행과 유실이 모두 허용되지 않습니다.

설계 결정

  • 경계 분리 — 시그널 생성은 상태 없이 두고, 주문 side effect와 계좌 상태는 실행 계층에서만 다루도록 나눴습니다. RabbitMQ fanout으로 시그널 1건을 계좌 N개에 배포합니다.
  • at-least-once + 멱등성 — publisher confirm, consumer manual ACK, DLQ로 전달을 보장하고, 중복 전달은 시간 슬롯 · 계좌 · 전략 · 시그널 ID를 묶은 멱등성 키로 흡수했습니다.
  • 계좌 단위 bulkhead — 주문 가능 수량, 포지션 동기화, 쿨다운을 계좌별로 격리해 한 계좌·거래소의 실패가 다른 계좌로 번지지 않게 했습니다.
  • 관측 — MySQL을 주문·체결의 기준 기록으로, Redis는 가격 캐시로만 제한하고, Prometheus·Grafana로 처리량 · 지연 · DLQ · 계좌별 실패율을 추적했습니다.

Python → Rust 점진 전환

Celery와 asyncio가 섞인 Python 실행 계층은 24/7 코인 주문 영역에서 메모리와 이미지 크기, 런타임 일관성 문제가 커졌습니다. 코인 실행 계층만 전환 대상으로 정하고 Strangler Fig 방식으로 옮겼습니다. 두 구현이 RabbitMQ 경계에서 공존하고, 소비 주체는 feature flag로 바꾸고 되돌릴 수 있게 했습니다. 거래소 어댑터는 trait으로 계약을 고정하고, SQL은 sqlx 컴파일 타임 검증을 썼습니다.

STOA Investment · 2024–2026.06 · 전략 엔진·검증·라이브 운영 전담

기관형 자산배분 전략을 3-클릭으로 구독하는 상품으로 만들고, 그 엔진이 시뮬레이션과 실제 계좌에서 같은 결과를 내도록 만드는 작업이었습니다. 1,600+ 계좌 운용 인프라에 적용되었고 AUM 500억 원 이상, 서비스 매출 40% 기여로 이어진 상품의 엔진입니다.

  • Point-in-time 데이터 — 거시 지표는 발표일 기준으로 사용 가능 시점을 맞추고, 시그널 다음 거래일 체결을 원칙으로 해 미래 정보 유입을 막았습니다.
  • 상태 3계층 — 최신 최적화 결과 · 직전 승인 비중 · 실제 포지션을 따로 저장하고, 승인 비중과의 편차가 임계값 이하면 리밸런싱을 보류해 회전율을 관리했습니다.
  • 모듈 경계 — 국면 판별 · 공분산 전처리(EWM, Ledoit-Wolf, RMT, PD 보정) · 리스크 예산 · 꼬리위험 오버레이를 교체 가능한 모듈로 나누고, 주문 side effect는 7번 실행 계층에 위임했습니다.
