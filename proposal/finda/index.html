자연어 기반 금융 서비스 데이터 접근을 위한 신뢰성 레이어 고도화 제안

Trusted Financial Data Foundation Proposal

용어 정의. 본 문서에서 말하는 금융 서비스 데이터는 대출·신용·금리/한도 등 금융 도메인 데이터뿐 아니라, 사용자 행동 이벤트, 제품 퍼널, 파트너 응답, 운영 로그, 모델 결과처럼 금융 서비스 의사결정에 연결되는 데이터를 함께 포함합니다.

문서 목적 및 전제

본 문서는 핀다 Data Engineer 지원 과정에서, 공개자료 기반으로 핀다의 데이터 플랫폼 고도화 방향을 가설화하고 제가 어떤 문제정의와 기술적 접근으로 기여할 수 있는지 설명하기 위한 제안서입니다.
작성 기준: 공개자료 기반 추정. 핀다 내부 아키텍처·우선순위·거버넌스 정책은 비공개이므로, 모든 제안은 입사 후 Discovery 단계에서 검증·수정되어야 합니다.

1. Executive Summary

핀다는 대출 비교·신용관리·마이데이터·AI 대출예측으로 확장하며 금융 데이터의 활용 범위를 넓혀가고 있습니다. 공개자료 기준으로는 Databricks Lakehouse, Delta Lake, Spark Streaming, Unity Catalog 등을 도입해 기존 데이터웨어하우스의 비용·성능·거버넌스 문제를 개선한 이력이 확인됩니다.

저는 다음 고도화 과제 중 하나가 단순 데이터 적재나 분석 환경 구축을 넘어, 권한을 가진 구성원이 자연어로 금융 데이터를 질문하고, 그 답의 정의·품질·권한·근거를 함께 확인할 수 있는 Trusted Financial Data Foundation이라고 가정했습니다.

이 제안의 핵심은 새로운 프로토콜(MCP, Model Context Protocol 등) 자체를 크게 구축하는 것이 아닙니다. 기존 데이터 플랫폼 위에 권한, 의미, 품질, 리니지, 최신성, 감사 가능성을 결합해 데이터 접근의 신뢰도를 높이는 최소 레이어를 설계하는 것입니다.

2. 공개자료 기반 현황 추정

영역확인/추정 내용제안에 주는 의미
LakehouseDatabricks Lakehouse, Delta Lake, Spark Streaming, Unity Catalog 도입 사례가 확인됩니다.데이터·분석·AI 환경 통합과 거버넌스의 기반은 이미 존재한다고 가정할 수 있습니다.
WorkflowAirflow, CDC, Streaming 기반 파이프라인 고도화 정황이 확인됩니다.Airflow는 품질 검증, 상태 기록, 재처리 정책의 핵심 접점입니다.
Serving & InfraJD 기준 Iceberg, Flink, StarRocks, Kubernetes, Terraform이 명시되어 있습니다.Lakehouse 이후 실시간/준실시간 처리, OLAP serving, IaC 자동화 단계로 확장 중이라고 추정합니다.
AI & Model Operation공개자료 및 채용공고 기준, 금리/한도 예측, 신용점수 예측, FDS, CSS, 리스크 세그멘테이션 등 금융 모델의 기획·배포·모니터링이 주요 과제로 확인됩니다.데이터 플랫폼은 단순 분석 환경을 넘어 모델 결과의 근거, feature snapshot, 품질 상태, 성능 모니터링 컨텍스트를 함께 제공해야 합니다.

즉, 데이터 플랫폼의 신뢰성은 분석 편의성을 넘어 모델 결과의 근거·재현성·모니터링 가능성과도 직접 연결됩니다.

위 추정이 맞다면 다음 병목은 “데이터를 더 많이 쌓는 것”이 아니라, 조직의 다양한 직무가 각자의 권한 안에서 같은 데이터를 같은 의미로 이해하고, 그 결과를 신뢰할 수 있게 만드는 것일 가능성이 큽니다.

3. 문제 인식과 접근 원칙

가설. Lakehouse 이후의 병목은 Trust Context일 수 있다

공개자료상 Lakehouse 도입이 확인되는 만큼, 비용·성능·분석 환경 통합은 상당 부분 진전되었을 것으로 추정됩니다. 다음 병목은 사용자가 데이터와 AI 결과를 신뢰하기 위해 필요한 정의, 품질, 권한, 리니지, 최신성, 근거가 얼마나 쉽게 확인되는지일 수 있습니다.

설계 원칙. 자연어 데이터 접근은 권한·의미·근거를 함께 제공해야 한다

AI가 SQL 작성과 지표 탐색을 대신할수록 데이터 접근 장벽은 낮아집니다. 그러나 금융 도메인에서는 접근성이 높아질수록 권한 없는 데이터 노출, 잘못된 지표 해석, 오래된 데이터 기반 의사결정, 출처 없는 AI 응답의 위험도 함께 커집니다.

따라서 본 제안의 자연어 데이터 접근 레이어(이하 Financial Data Access Layer)는 단순 챗봇이 아니라, 권한·의미 계층·품질 상태·근거 정보를 결합해 자연어 데이터 접근을 안전하게 만드는 신뢰 기반 레이어로 다뤄져야 합니다. 다음 조건을 만족해야 합니다.

  • 사용자의 조직·직무·권한에 따라 조회 가능한 데이터와 지표를 제한합니다.
  • 자연어 질문을 승인된 지표 정의, 데이터 제품, 정책에 매핑합니다.
  • 민감정보와 개인신용정보는 기본적으로 마스킹, 집계, 최소 단위 제한을 적용합니다.
  • 결과에는 source, snapshot, freshness, quality status, query/audit id를 함께 반환합니다.

접근 방식. 특정 도메인 데이터 제품에서 작게 검증한다

전사 범용 자연어 데이터 시스템을 처음부터 크게 만드는 것은 위험합니다. 먼저 반복적으로 발생하는 단순 수치 확인형 질문과 분석 요청 로그를 분류하고, owner·description·품질 기준·freshness SLA가 정의된 표준 데이터 제품 또는 SSOT 후보 1~2개만 대상으로 제한해 검증합니다.

자연어 기반 데이터 접근의 정확도는 LLM 자체 성능보다, 어떤 데이터를 참고 대상으로 허용할지에 더 크게 좌우됩니다. 승인율·한도조회·대출 실행·금리/한도·FDS 이벤트처럼 조직마다 다르게 해석될 수 있는 용어는 표준 정의와 연결하고, 여러 후보가 매칭될 경우 데이터 계층, owner 유무, description 완성도, freshness, 품질 통과 여부, 권한 정책을 함께 고려해 신뢰도 기반 우선순위를 부여합니다. 기준을 충족하지 못한 질문은 답을 생성하지 않고, 추가 조건 요청·owner 확인 필요·권한 부족·품질 BLOCK 등의 상태로 반환합니다.

4. 권한 기반 자연어 데이터 접근 레이어 구조

본 제안은 MCP 서버의 세부 구현 방식, LLM provider, 통신 방식, 저장 스키마를 확정하는 문서가 아닙니다. 실제 구현 스택은 핀다 내부의 Databricks, Airflow, Catalog, 인증, BI/AI 도구 현황에 맞춰 결정되어야 합니다.

제안 범위는 아래 5개 레이어입니다.

Layer역할MVP 범위
Identity & Permission사용자 조직·직무·권한·민감도 정책을 확인합니다.SSO/RBAC/ABAC 등 기존 권한 체계와 연결되는 정책 확인 단계를 정의합니다.
Semantic & Metric자연어 질문을 승인된 지표·차원·필터·데이터 제품으로 매핑합니다.핵심 지표 5~10개, 용어 정의, 허용 필터, 최소 집계 단위를 등록합니다.
Safe Query & Serving안전한 조회 경로를 선택하고 비용·범위·민감도 제한을 적용합니다.임의 SQL보다 승인된 query template 또는 metric query를 우선합니다.
Trust Context데이터 품질, 최신성, owner, SLA, lineage, 제한사항을 제공합니다.핵심 테이블의 PASS/WARN/BLOCK 상태와 freshness를 기록합니다.
Evidence & Audit결과의 근거와 감사 가능성을 제공합니다.source table, snapshot, quality status, query/audit id를 반환합니다.

최소 요청 흐름

자연어 질문
→ 사용자 권한 확인
→ 질문 의도와 업무 목적 확인
→ 승인된 지표/표준 데이터 제품으로 매핑
→ 신뢰도·권한·품질 기준으로 답변 가능 여부 판단
→ 안전한 조회 실행
→ 결과 + 조회 기준 + 신뢰 상태 + 근거 + 해석 주의사항 반환
→ 감사 로그 저장

이 흐름의 목적은 모든 임직원이 자유롭게 데이터베이스에 접근하도록 만드는 것이 아닙니다. 각자의 권한 안에서 안전하게 질문하고, 답의 근거와 한계를 함께 이해할 수 있게 만드는 것입니다.

4주 MVP 배포 일정

주차목표주요 산출물
1주차Discovery & SSOT 후보 선정반복 질문·분석 요청 로그를 분류하고, MVP 데이터 제품 1~2개를 선정합니다. owner·description·freshness SLA·품질 기준 초안을 정의합니다.
2주차Trust Layer 핵심 컴포넌트 구축권한 정책 매핑, Semantic/Metric Registry, Quality & Freshness Gate(PASS/WARN/BLOCK)를 구현합니다.
3주차자연어 접근 MVP 통합신뢰도 기반 후보 선택 로직, Answerability Gate, Evidence Response Format을 통합하고 내부 테스트로 응답 정확도를 점검합니다.
4주차제한 배포 & 운영 검증소수 직무 대상 파일럿을 운영하고, audit log·정확도·답변 불가 사유·KPI를 모니터링한 뒤 배포 범위 확대 여부를 판단합니다.

배포 기준은 기능 개수보다 안전성입니다. MVP는 전사 공개가 아니라 권한이 명확한 소수 직무와 표준 데이터 제품을 대상으로 제한 배포하고, 답변 정확도·재현성·품질 실패 탐지·권한 위반 차단 여부를 확인한 뒤 확장합니다.

6. 지원자 관점의 기여 가능성

제가 이 문제에 기여할 수 있다고 보는 이유는 특정 MCP 구현 경험보다 금융 데이터가 실제 사용자 자산, 운영 시스템, 모델/전략 판단, 비즈니스 성과와 연결되는 환경을 다뤄봤기 때문입니다.

  • 금융 데이터 정합성: 백테스트/라이브 정합성, 재처리 가능성, 데이터 품질, 운영 추적성을 실제 운용 시스템에서 다뤘습니다.
  • Airflow 기반 파이프라인 현대화: DAG, Sensor, TaskGroup, Storage Adapter, Data Quality Gate, Metadata Tracking으로 수집·검증·저장 책임을 분리한 경험이 있습니다.
  • Backend Reliability: RabbitMQ/Celery, DLQ, manual ACK, idempotency, bulkhead, audit log 등 운영 신뢰성 패턴을 데이터 플랫폼에도 전이할 수 있습니다.
  • 작은 MVP부터 검증하는 방식: 내부 도메인을 단정하지 않고, 핵심 데이터 제품·사용자·운영 병목을 학습한 뒤 작게 구현하고 검증하는 접근을 선호합니다.

결국 Trusted Financial Data Foundation은 신규 플랫폼을 크게 만드는 제안이 아닙니다. 핀다가 이미 구축한 데이터 플랫폼 위에 정의·품질·권한·리니지·최신성·자연어 접근·AI 근거 컨텍스트를 얹어 데이터 사용의 신뢰도와 전사 활용도를 높이는 고도화 방향입니다.
